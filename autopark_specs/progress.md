- Дата: 2026-10-17

- Перевірено: `configure_mappers()` та генерація OpenAPI успішні; MySQL `SELECT 1` успішний; фактичні таблиці, стовпці, ключі та зовнішні ключі прочитані. `TestClient` недоступний через відсутній у середовищі `httpx2`.
- Endpoint-и: `/health`, `/db-check`; GET/POST `/companies`, GET `/companies/{company_id}`; GET/POST `/buses`, GET `/buses/{bus_id}`; GET/POST `/drivers`, GET `/drivers/{driver_id}`; GET/POST `/routes`, GET `/routes/{route_id}`; GET/POST `/driver-routes`, DELETE `/driver-routes/{driver_id}/{route_id}`.
- Результат: усі п'ять роутерів включені в застосунок і відображаються в OpenAPI. Фактична БД має таблиці `companies`, `buses`, `drivers`, `routes`, `driver_routes`.

Також `companies.name` у БД має довжину 120, а ORM обмежує її до 100. `TestClient` не працює без пакета `httpx2`; автоматизованих тестів проєкту не знайдено. Інші CRUD-операції, пагінація, маршрути водія, фільтри, frontend і наскрізні сценарії відсутні або ще не перевірені.
- Точний план наступної ітерації: у межах ітерації 01 привести typed ORM усіх п'яти моделей у відповідність до фактичної схеми та FK/PK, обов'язково врахувати `companies.phone`, не змінювати БД, і перевірити mapper-и, імпорт і запуск.
- Підтвердження користувача для наступної ітерації: телефон компанії має бути обов'язковим; виконання наступної ітерації очікує окремої команди.

## Ітерація 05 — Надійність API
- Дата: 2026-10-17
- Ітерація: 05 — надійність API
- Реалізовано: додано rollback і зрозумілий `409` для `IntegrityError` при видаленні автобусів і водіїв. Перевірено rollback та відповіді для наявної обробки конфліктів у решті CRUD і призначеннях. `/db-check` повертає лише загальний `503` без деталей драйвера/DSN. Валідаційні схеми мають обов'язкові поля та обмеження довжин, діапазонів і пробілів. CORS не додавався: frontend відсутній і між-origin запит наразі не потрібний. README доповнений описом 503, 409 і рішенням щодо CORS.
- Перевірено: компіляція backend; ORM mapper-и й OpenAPI; OpenAPI містить очікувані успішні, `404`, `409`, `422` та `503` відповіді для перевірених операцій; невалідні payload-и дають Pydantic `ValidationError` (FastAPI відповідає `422`); штучно змодельовані помилки FK для DELETE повертають `409`, виконують rollback і зберігають записи; `/db-check` повертає безпечний `503` без витоку помилки; діагностики Pylance по workspace відсутні; `git diff --check`.
- Результат: відомі очікувані помилки мають сталі відповіді, транзакції відновлюються після помилок цілісності, секрети з DB URL не повертаються клієнту.
- Відомі проблеми: MySQL не перевірено, бо `DATABASE_URL` у середовищі не задано; реальні HTTP transport-тести не виконувалися (`httpx2` відсутній). CORS потрібно додати лише якщо frontend буде відкриватися з іншого origin.
